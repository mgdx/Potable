# Audit de sécurité — Potable 1.0.0 — 2026-10-25

## Contexte

- **Commit audité** : `3214ada` (`docs: add screenshots in English and French, and the APK size`).
- **Modules couverts** : `:app` (main et debug), `:data`, `:core` — 151 fichiers Kotlin, manifestes, `res/xml/`, règles R8, catalogue `gradle/libs.versions.toml`, graphe `releaseRuntimeClasspath`.
- **SDK** : minSdk 26, targetSdk 37, compileSdk 37. R8 et réduction des ressources actifs en release.
- **Méthode** : revue statique selon le skill `android-securite` (manifeste et composants exportés, stockage, secrets, TLS, WebView, intents et PendingIntent, providers, cryptographie, injection, journaux et presse-papier, permissions, dépendances, minification). Manifestes fusionnés produits par `./gradlew :app:processReleaseMainManifest :app:processDebugMainManifest` et lus en entier. Aucun test sur appareil (pas d'adb dans cette session) : les points marqués « à confirmer dynamiquement » sont à passer au skill `android-test`.
- **Références** : `SPEC.md` §2, §7, §10 ; `docs/decisions.md` ; `docs/privacy-policy.md` ; `docs/release.md` ; `SECURITY.md`.

### Biens à protéger

Potable n'a ni compte, ni jeton, ni secret serveur. Les biens sont :

1. **La liste des communes suivies** (et les UDI mémorisées) : elle désigne, à quelques kilomètres près, où vit et où se rend la personne.
2. **La position** (SPEC §10 : jamais stockée, jamais transmise).
3. **L'intégrité de l'information sanitaire affichée** : un nom de commune associé aux résultats d'une autre, c'est une information de santé publique fausse.
4. **La promesse réseau** : un seul domaine, `hubeau.eaufrance.fr`, en HTTPS.

### Surface d'attaque

- `MainActivity`, **exportée** (lanceur) : extras d'intent lus par `Intent.alertTarget()`, et intent de lancement lu aussi par le `NavController` de Navigation Compose.
- Réponses HTTP de Hub'Eau (JSON, redirections, taille).
- Composants AndroidX fusionnés (WorkManager, ProfileInstaller, startup).
- En debug seulement : `DebugAlertsActivity` et `PreviewActivity`, exportées.

## Synthèse

Aucun constat critique ni élevé. L'application est sobre et son durcissement de base est bon : pas de WebView, pas de cryptographie maison, pas de journal, `PendingIntent` immuables et explicites, cleartext interdit, sauvegardes désactivées, release propre. ## Constats

### V1 — Noms arbitraires acceptés depuis les extras de l'activité exportée, affichés comme titre et enregistrés au suivi

- **Gravité** : moyenne
- **Statut** : corrigé (`5a826b0`) — l'intent ne porte plus que les codes ; noms pris du suivi, sinon du référentiel, rien pour une commune inconnue
- **Emplacement** : `app/src/main/java/io/github/mgdx/potable/alert/AlertIntent.kt:81-94` ; usage dans `app/src/main/java/io/github/mgdx/potable/ui/PotableNavHost.kt:205-211`, `app/src/main/java/io/github/mgdx/potable/ui/sheet/SheetScreen.kt:96-97`, `app/src/main/java/io/github/mgdx/potable/ui/sheet/SheetViewModel.kt:139`
- **Bien exposé** : intégrité de l'information sanitaire ; liste des suivis
- **Profil d'attaquant** : application tierce installée, sans permission particulière
- **Chemin d'atteinte** : l'appli tierce lance `MainActivity` (exportée, `AndroidManifest.xml:48-58`) avec les extras `io.github.mgdx.potable.extra.COMMUNE`/`UDI` (codes valides d'une commune A) et `COMMUNE_NAME`/`UDI_NAME` (le nom d'une commune B) → `sheetTarget()` valide les codes mais garde les noms tels quels (seulement tronqués à 200 caractères) → la fiche affiche les résultats et la conclusion ARS de A sous le titre de B ; si la personne touche « Suivre », `follows.follow(communeCode, communeName, …)` enregistre le faux nom, que les notifications d'alerte reprennent ensuite.
- **Extrait** :
  ```kotlin
  // AlertIntent.kt:83-90
  val commune = getStringExtra(EXTRA_COMMUNE)?.takeIf { CODE.matches(it) } ?: return null
  val udi = getStringExtra(EXTRA_UDI)?.takeIf { CODE.matches(it) } ?: return null
  return SheetTarget(
      communeCode = commune,
      udiCode = udi,
      communeName = name(EXTRA_COMMUNE_NAME) ?: commune,
      udiName = name(EXTRA_UDI_NAME) ?: udi,
  )
  ```
- **Impact** : une appli quelconque peut faire afficher par Potable, avec sa crédibilité et ses données réelles, « eau non conforme » sous le nom de la commune de la personne (alarme injustifiée), ou une eau conforme sous le nom d'une commune en restriction (fausse réassurance). Le faux libellé survit au suivi. `SECURITY.md` range explicitement « faire afficher autre chose que ce qu'il a lui-même choisi » dans le périmètre.
- **Correction recommandée** : ne plus faire confiance aux noms venus de l'intent. Les notifications ne visent que des unités suivies : résoudre la cible contre la table `suivi` (`FollowRepository.find(communeCode, udiCode)`) et prendre les noms en base ; ignorer l'intent si l'unité n'est pas suivie. Les extras de nom deviennent inutiles.

### V2 — L'intent de lancement de l'activité exportée pilote directement le graphe de navigation

- **Gravité** : moyenne
- **Statut** : corrigé (`d41d2e7`) — intent assaini (liste blanche) avant le graphe, dans `onCreate` et `onNewIntent` ; `sample` sans fiche quitte l'écran ; `NavigationIntentTest`
- **Emplacement** : `app/src/main/java/io/github/mgdx/potable/MainActivity.kt:30-64` (aucun nettoyage de l'intent avant `PotableNavHost`) ; `app/src/main/java/io/github/mgdx/potable/ui/PotableNavHost.kt:232-242` (`rememberNavController()` + `NavHost`), `:365-371` (`getBackStackEntry(Routes.SHEET)`)
- **Bien exposé** : intégrité de l'affichage, disponibilité
- **Profil d'attaquant** : application tierce installée, sans permission particulière
- **Chemin d'atteinte** : à la création du graphe, le `NavController` lié à l'activité appelle `handleDeepLink(activity.intent)`. Navigation 2.10.2 (vérifié dans `navigation-runtime-android-2.10.2.aar`, `NavController.class`) lit pour cela les extras `android-support-nav:controller:deepLinkIds`, `…:deepLinkArgs` et `…:deepLinkExtras`, indépendamment de tout `deepLinks` déclaré. Les identifiants des destinations Compose se déduisent de leur route. Une appli tierce peut donc empiler n'importe quelles destinations (`sheet`, `history`, `timeline`, `udis`, `sample`) avec n'importe quels arguments :
  1. contournement complet de la validation de `AlertIntent.kt` (regex des codes, borne de 200 caractères sur les noms) — mêmes effets que V1, sans limite de forme ;
  2. `sample/{sample}` sans fiche en dessous : `navController.getBackStackEntry(Routes.SHEET)` lève `IllegalArgumentException` → plantage de l'appli à chaque lancement de cette forme.
- **Extrait** :
  ```kotlin
  // PotableNavHost.kt:368-371
  ) { entry ->
      // The sheet's entry is always below this one: it is the only way here.
      val sheetEntry = remember(entry) { navController.getBackStackEntry(Routes.SHEET) }
  ```
- **Impact** : usurpation d'affichage (comme V1) et déni de service local déclenchable à volonté. La passerelle `DisclaimerGate` reste en place (le graphe n'est composé qu'après l'acceptation), mais elle ne protège pas une installation où l'avertissement a déjà été accepté.
- **Correction recommandée** : retirer de l'intent de l'activité, avant toute composition, les extras réservés de Navigation (ou remplacer `intent` par une copie limitée à l'action et aux extras d'alerte, une fois `alertTarget()` lue), dans `onCreate` comme dans `onNewIntent`. Rendre en outre la route `sample` robuste à l'absence de fiche (retour arrière plutôt qu'exception).
- **Confiance** : lecture du code de l'appli et présence des clés dans la bibliothèque confirmées ; atteignabilité de bout en bout à confirmer sur appareil (`adb shell am start` avec un tableau d'entiers en extra).

### V3 — Redirections suivies vers n'importe quel hôte HTTPS

- **Gravité** : faible
- **Statut** : corrigé (`2e613c9`) — aucune redirection suivie, une 3xx devient `DataError.Http`
- **Emplacement** : `app/src/main/java/io/github/mgdx/potable/AppContainer.kt:36` ; `data/src/main/kotlin/io/github/mgdx/potable/data/HubEauClient.kt:38-45`
- **Bien exposé** : promesse réseau (SPEC §10 « un seul domaine contacté »), adresse IP et codes des communes suivies
- **Profil d'attaquant** : serveur Hub'Eau compromis, mal configuré, ou un intermédiaire capable de répondre au nom de `hubeau.eaufrance.fr` avec un certificat valide
- **Chemin d'atteinte** : `OkHttpClient()` garde ses défauts `followRedirects = true` et `followSslRedirects = true` ; `HubEauClient` n'y touche pas → un `302 Location: https://tiers.example/…` est suivi silencieusement, la réponse du tiers est analysée et affichée comme une donnée Hub'Eau. Le passage en `http://` est, lui, bloqué par `network_security_config.xml` (cleartext interdit, vérifié par OkHttp sur Android).
- **Extrait** :
  ```kotlin
  // AppContainer.kt:35-36
  /** The single HTTP client of the process; it only ever talks to Hub'Eau. */
  private val http: OkHttpClient by lazy { OkHttpClient() }
  ```
- **Impact** : l'appli peut contacter un autre domaine que celui qu'elle annonce, lui révéler l'IP et les codes des communes suivies (y compris depuis la tâche d'alerte périodique), et afficher un contenu qui ne vient pas de Hub'Eau. `SECURITY.md` cite « une redirection suivie hors de Hub'Eau » comme faille à signaler.
- **Correction recommandée** : désactiver le suivi des redirections (Hub'Eau n'en a pas besoin, à vérifier dans `docs/hubeau-api.md`), ou n'en accepter qu'en HTTPS vers `hubeau.eaufrance.fr` via un intercepteur réseau ; traiter une 3xx comme `DataError.Http`.

### V4 — Corps de réponse lu en mémoire sans borne

- **Gravité** : faible
- **Statut** : corrigé (`28602b5`) — corps borné à 32 Mio, `DataError.Format` au-delà
- **Emplacement** : `data/src/main/kotlin/io/github/mgdx/potable/data/HubEauClient.kt:126-131`
- **Bien exposé** : disponibilité de l'appli et de la tâche d'alerte
- **Profil d'attaquant** : serveur Hub'Eau compromis (ou réponse anormale très volumineuse)
- **Chemin d'atteinte** : `response.body.string()` charge tout le corps en mémoire avant l'analyse JSON → un corps de plusieurs centaines de Mo (ou un flux sans fin) provoque un `OutOfMemoryError`, qui n'est pas une `IOException` et n'est pas rattrapé : l'appli plante, ou le worker meurt à chaque période.
- **Extrait** :
  ```kotlin
  http.newCall(request).execute().use { response ->
      if (response.code != HTTP_OK && response.code != HTTP_PARTIAL) {
          throw DataError.Http(response.code)
      }
      response.body.string()
  }
  ```
- **Impact** : déni de service, uniquement depuis le serveur. `SECURITY.md` met dans le périmètre « une réponse de l'API, même hostile, qui fait planter l'application ».
- **Correction recommandée** : borner la lecture (taille maximale mesurée sur les plus grosses réponses légitimes, `size` = 20 000 lignes, avec une marge large), refuser au-delà par une `DataError` dédiée ou `DataError.Format`.

### V5 — Choix d'UDI des communes consultées conservés indéfiniment, sans moyen de les effacer

- **Gravité** : faible (vie privée)
- **Statut** : corrigé (`bc6e363`) — « Vider le cache » oublie l'UDI des communes non suivies ; pas de durée de vie (`docs/decisions.md`)
- **Emplacement** : `data/src/main/kotlin/io/github/mgdx/potable/data/preferences/AppPreferences.kt:117-122, 176` ; `app/src/main/java/io/github/mgdx/potable/ui/settings/SettingsViewModel.kt:210-215` (`confirmPurge` n'appelle que `water.purgeCache()`)
- **Bien exposé** : historique des communes consultées (≈ lieux d'intérêt de la personne)
- **Profil d'attaquant** : personne ayant l'appareil déverrouillé en main avec accès aux données de l'appli (root, débogage) ou analyse forensique ; aucune autre appli ne peut lire ce fichier
- **Chemin d'atteinte** : chaque commune à plusieurs UDI consultée, même sans la suivre, laisse une clé `udi_<code INSEE>` dans le DataStore `preferences` → ni la rétention, ni « Vider le cache », ni le retrait d'un suivi ne la suppriment.
- **Extrait** :
  ```kotlin
  override suspend fun rememberUdi(communeCode: String, udiCode: String) {
      store.edit { it[udiKey(communeCode)] = udiCode }
  }
  ...
  fun udiKey(communeCode: String) = stringPreferencesKey("udi_$communeCode")
  ```
- **Impact** : la liste des communes consultées s'accumule sans fin, alors que la politique de confidentialité affirme que « les recherches que vous tapez » et les données des communes non suivies ne sont pas conservées. La politique mentionne bien le choix d'UDI : ce n'est pas une contradiction, mais la seule façon de l'effacer est de vider les données de l'appli dans Android.
- **Correction recommandée** : rattacher ces clés à une durée (ou au plus N communes récentes), et les effacer avec « Vider le cache » ; mettre à jour `docs/privacy-policy.md` en conséquence.

### I1 — `DebugAlertsActivity` exportée sans permission (debug seulement)

- **Gravité** : info
- **Statut** : corrigé (`77a1ba9`) — `android:permission="android.permission.DUMP"`
- **Emplacement** : `app/src/debug/AndroidManifest.xml:8-13` ; manifeste debug fusionné (`app/build/intermediates/merged_manifest/debug/processDebugMainManifest/AndroidManifest.xml`, `DebugAlertsActivity` `exported="true"`, sans `android:permission`). Absente du manifeste release fusionné (vérifié), et sa classe vit dans le source set `debug`.
- **Profil d'attaquant** : appli tierce sur un appareil où un APK **debug** est installé
- **Impact** : n'importe quelle appli peut lancer une vérification d'alerte (`action=run`, requêtes réseau sans contrainte) ou reculer les dates « dernier prélèvement vu » (`action=age`, fausses notifications « nouvelle analyse »). Le manifeste debug fusionné expose aussi `androidx.compose.ui.tooling.PreviewActivity` (exportée, apportée par `debugImplementation(ui-tooling)`). Sans conséquence tant qu'aucun APK debug n'est distribué.
- **Correction recommandée** : aucune obligatoire. Défense en profondeur possible : n'autoriser que le shell (`android:permission="android.permission.DUMP"` est accordé à `adb shell` et pas aux applis tierces) ; et garder un test qui vérifie l'absence de l'activité dans le manifeste release.

### I2 — Contenu des notifications sur l'écran verrouillé

- **Gravité** : info
- **Statut** : corrigé (`dfe2dee`) — `VISIBILITY_PRIVATE` et version publique générique
- **Emplacement** : `app/src/main/java/io/github/mgdx/potable/alert/AlertNotifier.kt:138-177` (titre « commune, UDI »), `:104-128` (résumé `InboxStyle` qui liste toutes les communes)
- **Profil d'attaquant** : personne qui voit l'écran verrouillé
- **Impact** : aucune `setVisibility` ni `setPublicVersion` : la visibilité par défaut (`VISIBILITY_PRIVATE`) suit le réglage système. Avec le réglage par défaut (« afficher tout le contenu »), le résumé affiche la liste des communes suivies sur l'écran verrouillé. Le comportement respecte le choix de la personne ; il n'y a pas de faille, seulement une donnée quasi-locale plus visible que nécessaire.
- **Correction recommandée** : fournir une `setPublicVersion` générique (« Nouvelles analyses disponibles », sans nom de commune) pour les notifications d'unité et le résumé.

## Recommandations de durcissement

- **Épinglage de certificat** : non recommandé ici. Le domaine est public et géré par un tiers qui peut changer d'autorité ; un épinglage mal entretenu casserait l'appli pour tous. Le gain face à une AC compromise ne justifie pas ce risque pour des données publiques.
- **En-tête `User-Agent`** : laissé à `okhttp/<version>` (documenté dans la politique de confidentialité). Ne pas y mettre la version de Potable, qui distinguerait davantage les utilisateurs.
- **Test de non-régression du manifeste release** : un test (ou une tâche Gradle) qui échoue si un composant `exported="true"` sans permission apparaît dans le manifeste release fusionné, hors `MainActivity`.

### Prompt — V1 : noms de commune et d'UDI acceptés depuis les extras de `MainActivity`

Corrige la vulnérabilité suivante dans Potable (dépôt `/home/leo/AndroidStudioProjects/Potable`, commit de base `3214ada`). Lis d'abord `CLAUDE.md` du dépôt (et ignore celui du dossier parent, qui décrit un autre projet).

**Problème.** `MainActivity` est exportée. Les extras de nom (`io.github.mgdx.potable.extra.COMMUNE_NAME`, `…UDI_NAME`) qu'elle reçoit sont affichés comme titre de la fiche et enregistrés tels quels si l'utilisateur suit l'unité, sans lien vérifié avec les codes de commune et d'UDI.

**Emplacement.** `app/src/main/java/io/github/mgdx/potable/alert/AlertIntent.kt:81-94`

```kotlin
val commune = getStringExtra(EXTRA_COMMUNE)?.takeIf { CODE.matches(it) } ?: return null
val udi = getStringExtra(EXTRA_UDI)?.takeIf { CODE.matches(it) } ?: return null
return SheetTarget(
    communeCode = commune,
    udiCode = udi,
    communeName = name(EXTRA_COMMUNE_NAME) ?: commune,
    udiName = name(EXTRA_UDI_NAME) ?: udi,
)
```

Usage : `ui/PotableNavHost.kt:205-211` (`openSheet`), `ui/sheet/SheetScreen.kt:96-97` (titre), `ui/sheet/SheetViewModel.kt:139` (`follows.follow(communeCode, communeName, udiCode, udiName)`).

**Chemin d'atteinte.** N'importe quelle appli installée, sans permission, lance `MainActivity` avec les codes valides d'une commune A et le nom d'une commune B : Potable affiche les résultats et la conclusion sanitaire de A sous le nom de B, et le faux nom est enregistré si la personne suit l'unité, puis repris par les notifications.

**Attendu.** Le nom affiché pour une cible venue d'un intent doit être celui que Potable connaît pour ces codes, jamais un texte fourni par l'appelant. Un intent visant une unité non suivie ne doit rien ouvrir.

**Direction de correction.** Les notifications ne visent que des unités suivies (`AlertNotifier` construit l'intent à partir d'un `Follow`). Résoudre donc la cible contre la base : à la réception (`MainActivity.onCreate`/`onNewIntent`, ou dans le `LaunchedEffect` de `PotableNavGraph`), appeler `container.follows.find(communeCode, udiCode)` et naviguer avec les noms du `Follow` trouvé ; ignorer la cible si `find` renvoie `null`. Retirer alors `EXTRA_COMMUNE_NAME`/`EXTRA_UDI_NAME` de `sheetIntent()` et `SheetTarget` (ou les conserver uniquement comme indice non affiché, mais le plus simple est de les supprimer). La lecture en base est suspendue : ne pas bloquer le thread principal. Alternative moins bonne : résoudre le nom de commune par `CommuneRepository.byCode()` — elle ne couvre pas le nom d'UDI et bute sur les codes de requête des communes déléguées.

**Contraintes.** Ne pas casser l'ouverture de la fiche depuis une notification (application fermée, ouverte, en arrière-plan), ni le résumé qui ouvre « My communes », ni l'ignorance des intents rejoués depuis les récents. Pas de nouvelle dépendance. Mettre à jour la décision correspondante dans `docs/decisions.md` (ligne du 2026-10-25 sur « Toucher une notification »).

**Vérification attendue.** Tests Robolectric existants des intents (`app/src/test/...`) mis à jour ; un test nouveau : un intent avec des codes d'une unité non suivie, ou avec un nom différent de celui en base, n'ouvre pas de fiche ou ouvre la fiche avec le nom de la base. `./gradlew check` vert. Vérifie aussi qu'aucun autre extra lu par une activité exportée n'est affiché sans contrôle : `grep -rn "getStringExtra\|getParcelableExtra\|intent\.data" app/src/main`.

### Prompt — V2 : extras de Navigation acceptés depuis l'intent de lancement

Corrige la vulnérabilité suivante dans Potable (dépôt `/home/leo/AndroidStudioProjects/Potable`, commit de base `3214ada`). Lis d'abord `CLAUDE.md` du dépôt (et ignore celui du dossier parent).

**Problème.** `MainActivity` est exportée et héberge un `NavHost` Compose. À la création du graphe, le `NavController` appelle `handleDeepLink(activity.intent)`, qui lit les extras réservés `android-support-nav:controller:deepLinkIds`, `android-support-nav:controller:deepLinkArgs` et `android-support-nav:controller:deepLinkExtras` (présents dans `NavController` de `navigation-runtime-android` 2.10.2). Une appli tierce peut ainsi ouvrir n'importe quelle route avec n'importe quels arguments, en contournant la validation de `alert/AlertIntent.kt`.

**Emplacement.** `app/src/main/java/io/github/mgdx/potable/MainActivity.kt:30-71` (intent transmis tel quel) ; `app/src/main/java/io/github/mgdx/potable/ui/PotableNavHost.kt:232-242` et `:365-371` :

```kotlin
) { entry ->
    // The sheet's entry is always below this one: it is the only way here.
    val sheetEntry = remember(entry) { navController.getBackStackEntry(Routes.SHEET) }
```

**Chemin d'atteinte.** Une appli installée sans permission lance `MainActivity` avec un tableau d'identifiants de destinations (déductibles des routes) et des bundles d'arguments : fiche, historique ou frise avec des codes et des libellés arbitraires ; ou route `sample/…` seule, et `getBackStackEntry(Routes.SHEET)` lève `IllegalArgumentException`, ce qui fait planter l'appli.

**Attendu.** Le graphe de navigation ne doit être piloté que par l'appli elle-même. Les seules entrées externes acceptées restent les cibles d'alerte validées de `AlertIntent.kt`. Aucune route ne doit pouvoir faire planter l'appli quand elle est ouverte sans son écran parent.

**Direction de correction.** Dans `MainActivity`, après avoir lu `alertTarget()` et avant `setContent`, remplacer l'intent de l'activité (`setIntent`) par une version assainie : soit retirer explicitement les trois extras réservés de Navigation, soit, plus robuste, ne garder que l'action et les extras d'alerte connus. Faire de même dans `onNewIntent`. Vérifier en lisant la source de Navigation 2.10.2 (`NavController.handleDeepLink`) qu'aucun autre canal n'est lu (données `ACTION_VIEW` : aucune `deepLinks` n'est déclarée dans le graphe, donc pas de correspondance). En complément, rendre la route `sample` robuste : si aucune entrée `SHEET` n'existe dans la pile, revenir en arrière (`navigateUp`) au lieu de lever une exception (`runCatching` sur `getBackStackEntry` ou recherche dans `currentBackStack`).

**Contraintes.** Ne pas casser l'ouverture depuis les notifications (dépend des extras d'alerte), la restauration après rotation ou mort du processus (l'état sauvegardé du `NavController` ne passe pas par l'intent), ni le démarrage normal par le lanceur. Pas de nouvelle dépendance. Consigner la décision dans `docs/decisions.md`.

**Vérification attendue.** Test Robolectric (`ActivityScenario` ou test de la fonction d'assainissement) : un intent portant `android-support-nav:controller:deepLinkIds` ne change pas la destination de départ ; la route `sample` sans fiche ne lève rien. `./gradlew check` vert. Sur appareil (skill `android-test`, si un appareil est attribué) : `adb shell am start -n io.github.mgdx.potable/.MainActivity --eia android-support-nav:controller:deepLinkIds <ids>` n'ouvre rien d'autre que l'écran normal et ne plante pas. Vérifie aussi qu'aucune autre activité exportée n'héberge de `NavHost` : `grep -rn "rememberNavController\|NavHost(" app/src`.

### Prompt — V3 : redirections suivies hors de `hubeau.eaufrance.fr`

Corrige la faiblesse suivante dans Potable (dépôt `/home/leo/AndroidStudioProjects/Potable`, commit de base `3214ada`). Lis d'abord `CLAUDE.md` du dépôt (et ignore celui du dossier parent).

**Problème.** Le client HTTP garde les défauts d'OkHttp (`followRedirects = true`, `followSslRedirects = true`) : une réponse 3xx de Hub'Eau vers un autre hôte HTTPS est suivie sans contrôle, alors que SPEC §10 et `docs/privacy-policy.md` promettent qu'un seul domaine est contacté.

**Emplacement.** `app/src/main/java/io/github/mgdx/potable/AppContainer.kt:36`

```kotlin
private val http: OkHttpClient by lazy { OkHttpClient() }
```

et `data/src/main/kotlin/io/github/mgdx/potable/data/HubEauClient.kt:38-45` (le `newBuilder()` qui configure les délais).

**Chemin d'atteinte.** Un serveur Hub'Eau compromis ou mal configuré (ou un intermédiaire disposant d'un certificat valide pour ce domaine) répond `302 Location: https://autre-domaine/…` : l'appli, y compris la tâche d'alerte en arrière-plan, envoie l'IP et les codes des communes suivies à ce domaine et affiche sa réponse comme une donnée Hub'Eau. Les redirections vers `http://` sont déjà bloquées par `network_security_config.xml`.

**Attendu.** Aucune requête ne doit pouvoir partir vers un autre hôte que `hubeau.eaufrance.fr`, quelle que soit la réponse du serveur.

**Direction de correction.** Dans `HubEauClient` (c'est lui qui connaît l'hôte, et le réglage reste vrai si l'`OkHttpClient` partagé change), ajouter `.followRedirects(false).followSslRedirects(false)` au `newBuilder()`. Une 3xx tombe alors dans le contrôle existant et devient `DataError.Http(code)`. Vérifier dans `docs/hubeau-api.md` que l'API n'utilise aucune redirection légitime ; si c'était le cas, préférer un intercepteur réseau (`addNetworkInterceptor`) qui refuse toute requête dont `url.host != baseUrl.host` ou `!url.isHttps`. Consigner le choix dans `docs/decisions.md`.

**Contraintes.** Ne pas changer les délais, la distinction `Timeout`/`Network`, ni l'acceptation de 206. Pas de nouvelle dépendance.

**Vérification attendue.** Test dans `data/src/test` avec `mockwebserver3` (déjà dans le catalogue) : le serveur répond `302` avec un `Location` vers un second `MockWebServer` ; le client lève `DataError.Http(302)` et le second serveur ne reçoit aucune requête (`requestCount == 0`). `./gradlew :data:testDebugUnitTest check` vert. Vérifie aussi qu'aucun autre `OkHttpClient` n'est créé : `grep -rn "OkHttpClient" app/src/main data/src/main`.

### Prompt — V4 : corps de réponse lu sans borne

Corrige la faiblesse suivante dans Potable (dépôt `/home/leo/AndroidStudioProjects/Potable`, commit de base `3214ada`). Lis d'abord `CLAUDE.md` du dépôt (et ignore celui du dossier parent).

**Problème.** `HubEauClient.get()` lit tout le corps de réponse en mémoire avec `response.body.string()`, sans taille maximale. Une réponse démesurée provoque un `OutOfMemoryError`, qui n'est pas rattrapé et fait planter l'appli ou la tâche d'alerte.

**Emplacement.** `data/src/main/kotlin/io/github/mgdx/potable/data/HubEauClient.kt:126-131`

```kotlin
http.newCall(request).execute().use { response ->
    if (response.code != HTTP_OK && response.code != HTTP_PARTIAL) {
        throw DataError.Http(response.code)
    }
    response.body.string()
}
```

**Chemin d'atteinte.** Un serveur Hub'Eau compromis, ou une anomalie côté API, renvoie un corps de plusieurs centaines de Mo ou sans fin : plantage à chaque consultation, et à chaque passage du worker. `SECURITY.md` range ce cas dans le périmètre.

**Attendu.** Une réponse trop grosse doit produire une erreur de données ordinaire (affichée comme les autres erreurs, réessayable), jamais un plantage.

**Direction de correction.** Fixer une taille maximale (constante documentée dans le `companion object`, calibrée sur la plus grosse réponse légitime : `resultats_dis` avec `size` = 20 000 lignes et les champs demandés ; mesurer, puis prendre une marge large, de l'ordre de quelques dizaines de Mo). Refuser d'emblée si `body.contentLength()` dépasse la limite, puis lire la source en comptant les octets (Okio : `source.request(limit + 1)` puis contrôle de `buffer.size`) et lever une `DataError.Format` (ou une nouvelle variante si l'interface doit la distinguer) au-delà. Garder le décodage UTF-8 de `string()`.

**Contraintes.** Ne pas casser les historiques longs (fenêtre maximale, paramètre à nombreuses mesures) : la limite doit laisser passer largement les réponses réelles. Pas de nouvelle dépendance. Consigner la limite et sa mesure dans `docs/decisions.md`.

**Vérification attendue.** Test `mockwebserver3` dans `data/src/test` : un corps juste sous la limite passe, un corps au-dessus (avec et sans `Content-Length`, en chunked) lève l'erreur attendue sans `OutOfMemoryError`. `./gradlew :data:testDebugUnitTest check` vert. Vérifie aussi qu'aucune autre lecture de réseau ou de fichier externe n'est faite sans borne : `grep -rn "\.string()\|readBytes()\|readText()" data/src/main app/src/main`.

### Prompt — V5 : choix d'UDI conservés indéfiniment

Corrige la faiblesse de vie privée suivante dans Potable (dépôt `/home/leo/AndroidStudioProjects/Potable`, commit de base `3214ada`). Lis d'abord `CLAUDE.md` du dépôt (et ignore celui du dossier parent), puis `SPEC.md` §7 et §10 et `docs/privacy-policy.md`.

**Problème.** Chaque commune à plusieurs UDI consultée, même sans être suivie, laisse une clé `udi_<code>` dans le DataStore `preferences`. Ces clés ne sont soumises à aucune rétention et ni « Vider le cache », ni le retrait d'un suivi ne les effacent : l'appli accumule l'historique des communes consultées.

**Emplacement.** `data/src/main/kotlin/io/github/mgdx/potable/data/preferences/AppPreferences.kt:117-122` et `:176`

```kotlin
override suspend fun rememberUdi(communeCode: String, udiCode: String) {
    store.edit { it[udiKey(communeCode)] = udiCode }
}
...
fun udiKey(communeCode: String) = stringPreferencesKey("udi_$communeCode")
```

et `app/src/main/java/io/github/mgdx/potable/ui/settings/SettingsViewModel.kt:210-215` (`confirmPurge` n'appelle que `water.purgeCache()`).

**Chemin d'atteinte.** Une personne ayant accès aux données de l'appli (appareil rooté, débogage, analyse forensique) lit la liste des communes consultées depuis l'installation. Aucune autre appli ne peut lire ce fichier.

**Attendu.** La trace des communes consultées doit être bornée dans le temps ou en nombre, et effaçable par l'utilisateur depuis l'appli.

**Direction de correction.** Deux options, à trancher et à consigner dans `docs/decisions.md` : (a) effacer toutes les clés `udi_*` dans « Vider le cache » (ajouter une méthode `forgetRememberedUdis()` à `AppPreferences`, implémentée dans `DataStoreAppPreferences` en retirant les clés au préfixe `udi_`, appelée par `confirmPurge`), et/ou (b) limiter le nombre de choix mémorisés (par exemple les N plus récents, en stockant un horodatage) ou les soumettre à la durée de rétention. L'option (a) est la plus simple et suffit à rendre la trace effaçable ; (b) la borne sans action de l'utilisateur. Garder le choix d'UDI des communes **suivies** (la table `suivi` le porte déjà). Mettre à jour `docs/privacy-policy.md` (sections « Vos réglages » et « Vider le cache ») et le texte de confirmation de la purge s'il décrit ce qui est effacé (chaînes en anglais et en français, `res/values*/strings.xml`).

**Contraintes.** Ne pas casser la reprise directe sur l'UDI mémorisée pour une commune consultée à nouveau (avant purge). Aucune chaîne codée en dur. Pas de nouvelle dépendance.

**Vérification attendue.** Test de `DataStoreAppPreferences` dans `data/src/test` : après `rememberUdi` sur deux communes puis la purge, `rememberedUdi` renvoie `null` pour les deux ; les autres réglages (thème, rétention, alertes, avertissement accepté) sont intacts. Test de `SettingsViewModel` : `confirmPurge` appelle l'effacement. `./gradlew check` vert. Vérifie aussi qu'aucune autre trace de consultation n'est persistée : `grep -rn "PreferencesKey(\|@Entity" data/src/main`.
